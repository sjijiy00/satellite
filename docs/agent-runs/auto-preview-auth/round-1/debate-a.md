# Debater A — 회차 1 독립 의견

## 강점과 요구 충족

- `frontend/src/components/ProviderPreview.tsx:18`의 가시성 관찰과 `frontend/src/lib/providerPreviewQueue.ts:61,141`의 공유 큐·preview 전용 요청은 자동 표시와 중복/동시 요청 제한을 지향한다. `ManagedAssetAccess.tsx:42`의 원본 다운로드는 사용자 버튼에 남아 있다. 실제 DOM·네트워크 동작은 아직 검증되지 않았다.
- `backend/app/earthdata_store.py:176-239`는 사용자 범위 DPAPI 암호화, SID 결합, 기한과 용량 제한을 사용하며 저장 실패 시 평문으로 우회하지 않는다. 공개 browse와 인증, 제공처별 상태를 구분한다(`earthdata_auth.py:437-454`). 이는 연결 편의와 안전 경계에 유용하지만 실제 계정에서 지속 연결을 입증하지는 않는다.
- USGS/CDSE 원본 인증은 미연결로 명시된다. 공개 검색이 가능하다는 사실을 로그인·원본 접근 성공으로 혼동하지 않는 점은 좋으나, 여러 제공처의 로그인 유지라는 사용자 목표는 부분 충족이다. 계정·권한과 제품별 경로 실검증 없이 연결 완료로 표현할 수 없다.

## 회차 2 필수 수정

1. **높음: 폐기 실패 후 재시작 복원.** `earthdata_auth.py:120-123,155-172,415-434`는 삭제 실패에도 cookie를 삭제하고, `earthdata_store.py:172-174,233-239`의 실패 상태는 프로세스 메모리에만 남는다. 저장 권한이 복구된 뒤 재시작하면 복사된 기존 SID로 남은 grant를 복원할 수 있다. 코드상 위험이며 실제 악용은 검증하지 않았다. 동일한 쓰기 실패 저장소에 tombstone을 쓰는 것만으로는 보장할 수 없다. 독립적으로 신뢰할 수 있는 지속 폐기/키 무효화 수단을 마련하고 그 기록을 확인하기 전 복원하지 않도록 하거나, 이를 보장할 수 없다면 영속 복원을 기본 비활성화하는 보수적 방안을 권한다. 삭제 실패→복구→재시작→기존 SID 재사용, 재시도 및 갱신 중 로그아웃을 테스트해야 한다. 서버의 로컬 grant 폐기는 NASA 전체 토큰 철회와 구별한다.
2. **로그아웃 503 UI.** 서버는 `storage_disposed=false`를 반환하면서 cookie를 지우지만 `EarthdataConnection.tsx:69-83`은 일반 실패 메시지만 표시하고 기존 연결 표시·다른 탭/큐를 갱신하지 않는다. 503 본문을 처리해 디스크 폐기 미확인을 명시하고 인증 상태와 큐를 무효화·재조회해야 한다. cookie가 이미 사라진 뒤 재시도 성공을 기존 grant 폐기 증거로 취급해서는 안 된다.
3. **완료 판정 보류.** QA의 production build와 Playwright는 `spawn EPERM`으로 빌드 완료/브라우저 assertion 전에 실패했다(`qa.md`). 코드 결함이라고 단정할 근거도, 통과라고 할 근거도 없다. 허용된 실행 환경에서 격리 build 및 브라우저 E2E를 실행해 viewport·중복·지연 응답·원본 자동 요청 0·로그아웃 실패를 확인해야 한다. 권한 제약이 지속되면 미검증으로 남긴다.

## 검증 근거와 후속 사항

QA의 관련 backend 47 passed/1 skipped와 TypeScript 통과는 fixture 중심이다. 실제 DPAPI 왕복은 ACL mock을 사용했고 실제 ACL 준비·재시작 복원은 미검증이다. 프런트 큐 VM 검사는 담당자 보고이며 브라우저 증거가 아니다. 실제 NASA 로그인/갱신/파일 권한, Kakao 실조회, USGS/CDSE 인증 및 LIVE_STAC는 이번 검증에서 실행되지 않았다. 이전 `TEST_REPORT.md`의 실연결 결과를 이번 변경의 성공으로 전용하지 않는다.

후속 개선으로 공식 제공처별 권한·제품 매핑을 실제 계정으로 검증하고, `provider_transfer.py`의 DNS 검증과 연결 사이 재해석 가능성을 평가한다. 후자는 보안 보고의 미재현 가설이며 현재 확정 취약점으로 취급하지 않는다. 이번 의견은 다른 토론인의 의견을 보지 않은 독립 검토이며, 제품·테스트를 수정하거나 직접 테스트를 실행하지 않았다.

## B 의견에 대한 수용과 보완

B의 판단을 수용한다. 모든 지속 저장 쓰기와 제공처 폐기가 함께 실패하면 재시작을 넘는 폐기를 보장할 수 없다. 실패를 명시하고 운영자의 저장소 격리·복구와 제공처 측 철회 확인을 안내해야 한다. 독립적인 내구성 있는 폐기 기록이나 키 무효화가 실제로 기록되고 검증되는 경우에만 복원 차단을 보장할 수 있다. 그 보장이 준비되기 전에는 영속 저장·복원을 기본 비활성화하는 것이 적절하다. 다만 기본값 변경만으로 이미 저장된 grant가 폐기되는 것은 아니므로 기존 저장소는 확인 가능한 격리·폐기 전 재활성화해서는 안 된다.

로그아웃 503에서는 디스크 폐기 미확인을 구체적으로 표시하고 로컬 연결 표시와 미리보기 큐를 무효화하며 다른 탭에 통지하고 상태를 재조회해야 한다. 재조회나 SID 없는 재시도 성공을 디스크 폐기 성공으로 해석하지 않는다. 회차 2 검증은 삭제 실패 후 재시작·이전 SID 재사용 및 UI를 포함하되, fixture 결과와 실제 Windows ACL·재시작·제공처 철회 검증을 구분한다. `spawn EPERM`으로 중단된 build/E2E는 허용된 환경에서 완료하기 전까지 미검증이며, 실제 계정 접근도 별도 증거가 필요하다.
